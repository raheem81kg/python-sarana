# Complete Explanation: Steps 8 & 9

## 📚 Understanding Step 8: Code Generator (Deep Dive)

### What Problem Does It Solve?

**Problem:** We have a Sarana program as an Abstract Syntax Tree (AST), but computers can't execute ASTs directly. We need to convert it to a language that CAN be executed (Python).

**Solution:** The **code generator** walks the AST and emits equivalent Python code as strings.

---

### How Code Generation Works (Step by Step)

Let's trace through a complete example:

#### Input Sarana Code:
```sarana
bloom x = 10;
when (x > 5) {
    echo "big";
}
```

#### Step 1: Lexer → Tokens
```
[BLOOM, IDENTIFIER(x), ASSIGN, INTEGER(10), SEMICOLON,
 WHEN, LPAREN, IDENTIFIER(x), GREATER_THAN, INTEGER(5), RPAREN, LBRACE,
 ECHO, STRING("big"), SEMICOLON,
 RBRACE]
```

#### Step 2: Parser → AST
```python
Program(
    statements=[
        BloomStatement(
            name="x",
            value=Integer(10)
        ),
        WhenStatement(
            condition=BinaryOp(
                operator=">",
                left=Variable("x"),
                right=Integer(5)
            ),
            then_body=[
                EchoStatement(
                    expressions=[String("big")]
                )
            ],
            otherwise_body=None
        )
    ]
)
```

#### Step 3: Code Generator Walks AST

**The code generator is like a translator that visits each AST node:**

```python
class CodeGenerator:
    def __init__(self):
        self.indent_level = 0
        self.output = []  # Lines of Python code we're building
    
    def generate(self, program_node):
        # Start at the Program node
        self.visit_Program(program_node)
        return '\n'.join(self.output)
    
    def visit_Program(self, node):
        # Visit each statement in order
        for statement in node.statements:
            self.visit(statement)
    
    def visit_BloomStatement(self, node):
        # Translate: bloom x = 10  →  x = 10
        value_code = self.visit_expression(node.value)  # Returns "10"
        self.emit(f'{node.name} = {value_code}')       # Emits: "x = 10"
    
    def visit_WhenStatement(self, node):
        # Translate: when (x > 5) { ... }  →  if x > 5:
        condition_code = self.visit_expression(node.condition)  # Returns "(x > 5)"
        self.emit(f'if {condition_code}:')                      # Emits: "if (x > 5):"
        
        # Indent for the if body
        self.indent_level += 1
        
        # Visit statements inside the 'then' block
        for stmt in node.then_body:
            self.visit(stmt)
        
        # Dedent back
        self.indent_level -= 1
    
    def visit_EchoStatement(self, node):
        # Translate: echo "big"  →  print("big")
        expr_codes = [self.visit_expression(e) for e in node.expressions]  # Returns ['"big"']
        self.emit(f'print({", ".join(expr_codes)})')                       # Emits: 'print("big")'
    
    def visit_expression(self, node):
        # Handle different expression types
        if isinstance(node, Integer):
            return str(node.value)  # 10 → "10"
        elif isinstance(node, Variable):
            return node.name  # Variable("x") → "x"
        elif isinstance(node, String):
            return f'"{node.value}"'  # String("big") → '"big"'
        elif isinstance(node, BinaryOp):
            left = self.visit_expression(node.left)    # "x"
            right = self.visit_expression(node.right)  # "5"
            return f'({left} {node.operator} {right})' # "(x > 5)"
    
    def emit(self, code):
        # Add line of code with proper indentation
        indent = '    ' * self.indent_level
        self.output.append(indent + code)
```

```python

```

### Why PEMDAS Works

**Sarana Code:** `C = A + B * B`

**AST Structure:**
```
BinaryOp("+")
├── left: Variable("A")
└── right: BinaryOp("*")
          ├── left: Variable("B")
          └── right: Variable("B")
```

**Code Generation Walk:**
```python
def visit_expr_BinaryOp(node):  # Start with the "+" node
    left = visit_expression(node.left)   # Returns: "A"
    
    right = visit_expression(node.right) # This is the "*" node!
                                         # Recursively visits it
                                         # Returns: "(B * B)"
    
    return f'({left} {node.operator} {right})'
    # Returns: "(A + (B * B))"
```

**Generated Python:** `C = (A + (B * B))`

The **nested structure** of the AST automatically generates the correct parentheses!

## 🤔 Compiler vs Interpreter — The Full Picture

### What We Built

Your project has **BOTH** a compiler AND an interpreter. Here's why:

#### 1. **Interpreter** (src/interpreter.py)

**What it does:**
- Takes the AST
- Walks through it node by node
- **Executes** each instruction immediately
- Maintains a runtime environment (variables, functions)

**Example:**
```python
# When interpreter sees BloomStatement(name="x", value=Integer(10))
def visit_BloomStatement(self, node):
    value = self.evaluate(node.value)  # Evaluates to 10
    self.environment.set(node.name, value)  # Stores x=10 in memory
```

**Pros:** Fast development, immediate feedback  
**Cons:** Slower execution (interprets every time)

#### 2. **Compiler** (src/codegen.py)

**What it does:**
- Takes the AST
- Walks through it node by node
- **Generates** Python code as strings
- Writes to a `.py` file

**Example:**
```python
# When codegen sees BloomStatement(name="x", value=Integer(10))
def visit_BloomStatement(self, node):
    value_code = self.visit_expression(node.value)  # Returns "10"
    self.emit(f'{node.name} = {value_code}')        # Writes: "x = 10"
```

**Pros:** Produces standalone executable code  
**Cons:** Requires compilation step

### Types of Compilers

1. **Native Compiler** (like C compiler)
   - Sarana → Machine Code (.exe, binary)
   - Hardest to build
   - Fastest execution

2. **Source-to-Source Compiler / Transpiler** (what we built!)
   - Sarana → Python → Python interpreter → Execution
   - Medium difficulty
   - Good execution speed (Python is optimized)

3. **Bytecode Compiler** (like Java)
   - Sarana → Bytecode → Virtual Machine → Execution
   - Medium difficulty
   - Medium execution speed

We chose #2 (transpiler) because:
- ✅ Python is widely available
- ✅ Easier than generating machine code
- ✅ Still counts as "target code generation" for grading
- ✅ Generated code is readable (good for debugging/report)

## 🎯 Step 9: Main Entry Point (src/sarana.py)

### What Problem Does It Solve?

**Problem:** We have 5 separate modules (lexer, parser, semantic, interpreter, codegen) but no unified way to use them together.

**Solution:** `sarana.py` ties everything together into ONE function call that runs all phases.

### What It Does

```python
def compile_and_run(source_code):
    """
    One function that does EVERYTHING:
    1. Tokenize (lexer)
    2. Parse (parser)
    3. Analyze (semantic)
    4. Interpret (interpreter)
    5. Generate (codegen)
    
    Returns results from ALL phases in one object.
    """
```

### Why It's Important

#### Before (Without sarana.py):
```python
# User has to manually run each phase
from lexer import tokenize
from parser import parse
from semantic import analyze
from interpreter import interpret
from codegen import generate

code = "bloom x = 5; echo x;"

# Step 1
tokens = tokenize(code)

# Step 2
ast = parse(code)

# Step 3
errors = analyze(ast)

# Step 4
result = interpret(ast)

# Step 5
python_code = generate(ast)

# User has to manage errors from each phase...
```

#### After (With sarana.py):
```python
from sarana import compile_and_run

code = "bloom x = 5; echo x;"
result = compile_and_run(code)

# ONE call gets you EVERYTHING:
print(result.tokens)          # From lexer
print(result.ast)             # From parser
print(result.semantic_errors) # From semantic
print(result.output)          # From interpreter
print(result.generated_code)  # From codegen
```

## 🎓 Summary: What Makes This a Complete Compiler

### ✅ All Required Phases Present

1. **Lexical Analysis** (lexer.py)
   - Input: Raw source code string
   - Output: List of tokens
   - Removes comments, whitespace

2. **Syntax Analysis** (parser.py)
   - Input: Tokens
   - Output: Abstract Syntax Tree
   - Enforces grammar rules, PEMDAS

3. **Semantic Analysis** (semantic.py)
   - Input: AST
   - Output: List of semantic errors
   - Checks types, undefined variables, division by zero

4. **Target Code Generation** (codegen.py)
   - Input: AST
   - Output: Python source code string
   - Translates Sarana → Python
   - **THIS IS THE COMPILER!** (8 marks)

5. **Execution** (interpreter.py + generated .py files)
   - Two ways to execute:
     - Interpreter: Walks AST directly
     - Compiled: Run generated Python file

### ✅ Complete Data Flow

```
.sara file
   ↓ [Read]
Source code string
   ↓ [Lexer]
Tokens
   ↓ [Parser]
AST
   ↓ [Semantic]
AST + Errors
   ├→ [Interpreter] → Output
   └→ [Code Gen] → .py file → Execute → Output
```

### ✅ Yes, This IS a Compiler!

A compiler must:
1. ✅ Take source code in one language (Sarana)
2. ✅ Translate to another language (Python)
3. ✅ Produce executable output (generated .py files run with Python)
